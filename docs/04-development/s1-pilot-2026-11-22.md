## 2. 闭环步骤与证据

### 2.1 提交 → 入团队层 → 同步到第二成员

1. A 经 MCP `memory_propose {type: process, team: team-ops}` 提交《502 排障 SOP》
   → 提案落 `pending/PRO-000002.md`，frontmatter `scope: domain/team-ops`。
2. 人工审批（`memhub inbox approve PRO-000002`）→ 铸 ID `PRC-000004`，落
   `knowledge/groups/team-ops/process/`。**证据**：`knowledgeId: PRC-000004`。
3. `memhub sync push` → 中心仓 `master` 收到 `knowledge/groups/team-ops/process/PRC-000004.md`。
4. B `sync pull` → 本地 `indexedCount: 4`。
5. B 经 MCP 检索验证：
   - `memory_search {query:"502 网关 排障", team:"team-ops"}` → 命中 `PRC-000004`（score 6.863）；
   - `memory_preflight {intent:"502 排障 超时", team:"team-ops"}` → `status: ready`，
     pack 行 = `[PRC-000004] API 网关 502 排障 SOP — …`（上下文注入生效，tokens 50）；
   - `memory_get {id, full:true}` → 七步正文逐字完整（L2 无损）。

### 2.2 修订 → 版本升级（同一身份，不产生重复）

1. B 实战后提交修订：`memory_propose {supersedes:["PRC-000004"], team:"team-ops"}`
   → `PRO-000001`，frontmatter 带 `supersedes: PRC-000004`。
2. 审批 → **`knowledgeId: PRC-000004, version: 2`**（原地升级，`history/` 快照 v1）。
3. B push → A pull → A 侧 `get` 显示 `"version": 2`，`created` 保留 v1 时间戳、
   `updated` 前进——**身份稳定，无重复条目**。
4. 再迭代一版（B 现场证据，`version: 3`），A pull 后确认 v3。

### 2.3 冲突场景（仲裁已落地，见 ADR-0025）

A 与 B 对同一条目各自提出**分歧修订**（B：WAF 检查放第 9 步；A：WAF 前置到第 4 步）：

- 初版行为（v0.1.39）：B 的 v3 先入中心，A 的 v3' 审批成 v4 后 push，
  pre-pull rebase 干净，**v4 静默覆盖 v3**，无告警；B 的 v3 仅存于 `history/`。
  当时如实记录为 last-writer-wins 缺口（D06 待办）。
- **修复后行为（v0.1.40）**：提案自动记录 `supersedes_base`（所基于的目标版本）；
  审批时若目标已被他人推进 → **争议隔离**：不覆盖、提案保留、ledger 记
  `dispute.raised`；人工可 reject 或 `--override`（记 `dispute.overridden`）。
- **真实回放（v0.1.40）**：B 基于 v4 提交修订 → A 并发推进 v5 → B 审批被隔离
  （目标保持 v5、PRO-000006 保留、ledger 1 条 `dispute.raised`）→
  `--override`（note：团队评审确认 B 证据更贴合现场）→ v6 落地 +
  `dispute.overridden` 审计 → A pull 收敛到 v6。

**结论**：并发分歧不再静默覆盖；history/ 快照继续保证可溯；"当前真值"由人工
显式裁决（可解释、留审计）。语义冲突判定（谁对）仍交人工——符合 §9.3 先用规则。

## 3. 试点发现并修复的真缺陷

| # | 缺陷（真实触发） | 修复 |
|---|---|---|
| 1 | **根级 `.writer.lock` 误入中心仓历史**：任何获取/释放锁都造成 tracked 变更，`sync push` 的 pre-pull rebase 直接失败（`cannot rebase: You have unstaged changes`） | init 的 `.gitignore` 模板补 `.writer.lock`；中心仓 `git rm --cached` 清除；各 hub 本地补忽略 |
| 2 | **`memory_search` 完全不支持 team 维度**（只有 preflight 读 `MEMHUB_TEAM`）：团队知识在检索路径上永远不可见 | MCP 与宿主插件 `memory_search` 增加 `team` 参数（缺省读 `MEMHUB_TEAM`），并加团队可见性测试 |
| 3 | **`memory_propose` 硬编码 project 层**：宿主入口无法把知识提交到团队层 | 增加 `team` 参数 → `scope: domain/<teamId>`（仍走人工审批） |
| 4 | **审批实现三处分叉**：serve-panel 路径正确处理 `supersedes`，而 CLI `inbox approve` 与 MCP commit 各自实现、忽略 supersedes → 同标题修订被去重守卫误杀（`an accepted entry with the same title exists`） | 提取共享 `store.commitProposal`，CLI/面板/MCP 三面统一；CLI supersedes 回归测试 |
| 5 | **个人私有记忆无法经 MCP 写入**（用户核心诉求"写入个人记忆，按人划分"在宿主面缺失） | `memory_propose {private:true}` 直写 `knowledge-private/`（永不外流、无需团队审批），MCP 与宿主插件同步 |

配套回归：根仓 `160 passed`、插件 `10 passed`；新增覆盖 F01–F07、S1 修订、团队可见性、
private 直写共 17+ 个断言用例。

## 4. 结论与下一步

- **S1 验收通过**：两人、一团队、一类知识、一生产后端的完整闭环（提交→审批→推送→
  拉取→检索/注入→修订→再同步）在真实 GitHub 仓 + 真实 MCP 面上跑通。
- **D06 仲裁已落地（v0.1.40，ADR-0025）**：并发分歧隔离为争议（不覆盖、可解释、
  人工 `--override` 留审计）；语义冲突判定仍交人工。
- **S1 暴露的下一层问题**（按优先级）：
  1. **审批面一致性已修复**，但 MCP `memory_commit` 仍 fail-closed（设计如此），
     面板与 CLI 是仅有的人工通道——S2 前可考虑宿主内审批提示。
  2. 私有层跨机同步（`memhub personal sync`）在 S1 未纳入（个人线独立），
     F02 的合并语义已在 S0 修复并有双机测试。
- **冻结项**：腾讯节点继续作为对等节点（非 git 服务），部门自动化、向量召回、
  重排保持 S2 之后再议。
