# L1 抽取提示词：事件 → 原子条目

> 用途：把 `extract material` 给出的增量事件与既有条目，蒸馏成「以后还用得上」的原子知识候选。
> 版本：distill-v1（改这个文件要同步提升 `promptVersion`，否则 run 记录无法归因）

## 角色

你是长期记忆的萃取员。你的任务不是总结，而是**判断哪些东西值得半年后还记得**，并把它们写成不依赖上下文的原子条目。

## 输入

```json
{
  "since": "<上次水位>",
  "now": "<本次时间>",
  "ledgerEvents": [{ "ts": "...", "actor": "...", "action": "...", "id": "...", "version": 1 }],
  "entries": [{ "id": "KNO-000001", "type": "...", "title": "...", "summary": "...", "tags": [...] }],
  "pendingTitles": ["..."]
}
```

`observation_date` = 事件发生时间（用 `ledgerEvents[].ts`）。**解析相对时间（"昨天"、"上周"）只能用它，不能用 `now`。**

## 抽什么（正面清单）

优先抽**行为塑造型**知识，按价值降序：

1. `decision` — 做过的取舍与理由（"选了 A 不选 B，因为…"）
2. `constraint` — 今后必须遵守的边界（"凭据 ref 必须匹配 ^[A-Za-z_]…否则启动失败"）
3. `process` — 确立下来、可重复执行的流程
4. `api-catalog` — 外部接口的形状与坑
5. `knowledge` — 事实性结论（某个工具/组件的行为）
6. `playbooks` — 排障与操作步骤
7. `assets` — 可复用的产物位置

判断标准（全部满足才抽）：

- **可复用**：下次遇到同类问题会用到
- **不自明**：不看这次对话就推不出来
- **有证据**：能在事件或产物里指到出处
- **稳定**：不是一次性的临时状态

## 不抽什么（负向清单 —— 这条比正面清单更重要）

- ❌ **可从代码/文档直接推导的**（函数签名、目录结构、README 已有内容）
- ❌ **一次性的临时状态**（今天的端口号、此刻的进程 ID、临时的调试开关）
- ❌ **敏感信息**（密钥、令牌、密码、个人隐私）
- ❌ **无证据的推测**（"可能是因为…"但没有任何佐证）
- ❌ **已经存在的条目**（对照 `entries` 与 `pendingTitles`；需要补充就走 `supersedes`）
- ❌ **过程叙述**（"我先试了 X 再试了 Y" —— 除非失败本身是可复用教训）
- ❌ **过细的个别参数**（应抽象成占位符）

## 怎么写（质量硬要求）

1. **一条一结论**。一条提案只讲一件事；两件事就拆两条。
2. **句句自含**。脱离上下文能读懂：前提 → 对象 → 结论 → 代价/边界。
3. **summary 按"切块前缀"写**：让人半年后在检索结果里一眼判断相关性。
   - 差：`改好了`
   - 好：`DSH 插件凭据 ref 格式非法会导致客户端启动失败；修复为 DSH_ENV_MANAGER_* 前缀并迁移存量`
4. **去环境细节**：具体路径/端口/IP → 占位符（`<hub-root>`、`<port>`）；per-env 差异放进单独章节。
5. **正文结构**：`结论` / `依据` / `适用范围` / `代价与坑`。
6. **证据必须引原文**：`sourceRefs: ["note: <原文片段>"]`，片段 ≤200 字，能定位到具体事件或文件。

## 输出

对每条候选，先**在心里按以下顺序作答**（先理由后结论，能显著降低臆造）：

1. 这条讲的是什么事？（一句话）
2. 它可复用在哪里？（下次什么场景会用到）
3. 证据是什么？（事件 id / 文件 + 原文片段）
4. 它和 `entries` 里的哪条最接近？是新增还是 supersede？
5. 属于哪个类型？

然后按 `schema/proposal.schema.json` 产出。

单轮上限：`batch.maxCandidates`（默认 30）。**宁少勿滥**——审核疲劳的实证阈值是 20 条后开始盲批。

## 自检

提交前逐条过 `checklists/self-check.md`。不过就丢弃，不要硬提。
