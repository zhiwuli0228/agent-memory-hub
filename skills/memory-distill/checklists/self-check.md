# 提交前自检清单

> 每条候选都要过一遍。任一条不过就**丢弃**，不要勉强提交。
> 理由：一条坏记忆的代价远高于漏掉十条好记忆——它会长期污染检索结果，且没人会回头复查。

## A. 价值（不过就丢）

- [ ] **可复用**：能说出「下次什么场景会用到」，说不出 → 丢
- [ ] **不自明**：不看这次上下文就推不出来；从代码/文档能直接读到的 → 丢
- [ ] **非一次性**：不是此刻的临时状态（端口号、进程 ID、调试开关）→ 丢
- [ ] **稳定**：不会一周后就变；会变的要写清有效期（`expires_at`）

## B. 证据（没有就丢）

- [ ] `sourceRefs` 至少一条
- [ ] 引文是**原文片段**（≤200 字），不是自己复述的
- [ ] 引文能定位到具体事件 / 文件 / 会话
- [ ] 正文里出现的数字、路径、错误码，都能在证据里找到
- [ ] 无证据的推测一律丢弃（不要写「可能是因为」）

## C. 质量（不过就改）

- [ ] **一条一结论**：没有把两件事塞进一条
- [ ] **自包含**：title + summary 脱离上下文能读懂
- [ ] **summary 可检索**：包含关键实体与结论，不是「优化了一下」
- [ ] **无环境特定细节**（或已抽象为占位符）
- [ ] 正文有结构：结论 / 依据 / 适用范围 / 代价

## D. 去重（不过就改或丢）

- [ ] 与 `entries` 的标题/摘要比对过
- [ ] 与 `pendingTitles` 比对过（避免与待审重复）
- [ ] 如有高度相似条目 → 改用 `supersedes: ["KNO-xxxxxx"]` 而不是新建孪生
- [ ] 与既有条目**矛盾**时：不静默覆盖，走 supersede 并在正文说明「原结论错在哪」

## E. 类型与审批等级

- [ ] 类型选对（`decision`/`constraint`/`api-catalog` 会被逐条审批，其余可批量）
- [ ] 行为塑造型（会改变未来行为的）确实标成了 `decision`/`constraint`

## F. 接线（不过就整批作废重来）

- [ ] 每条都带 `origin: "distill"`
- [ ] 每条都带 `originId: "<RUN_ID>"`（同一批次同一个）
- [ ] 提交数 ≤ `batch.maxCandidates`
- [ ] 全部处理完才 `distill run finish`；中途失败用 `distill run fail`，不要 finish

## 最后一道保险

问自己：**「如果半年后我搜到这条，会觉得有用还是觉得浪费了 10 秒？」**

答案是后者 → 丢掉。
